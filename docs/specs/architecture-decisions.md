## 📌 문서 목적 및 개요
본 문서는 DormMate 서비스의 설계 및 개발 과정에서 마주한 기술적·기획적 복잡성을 걷어내고, **실제 280인 기숙사 현장 도메인 제약([domain-context.md](domain-context.md))과 사용자 심리(User Psychology)를 분석하여 내린 핵심 아키텍처 의사결정(ADR-001 ~ ADR-014)**을 기록합니다.

기술을 과시하기 위한 오버엔지니어링을 배제하고, **소프트웨어 공학의 YAGNI(You Aren't Gonna Need It)와 KISS(Keep It Simple, Stupid) 원칙에 입각해 최소한의 비용으로 최대한의 효과를 도출한 실무적 근거**를 담고 있습니다.

## ADR-001: 기숙사 계정 관리 패러다임 전환

### 1. 배경 및 문제 (Context)
* 초기 기획은 일반적인 웹 서비스처럼 **"거주자가 회원가입 신청(`signup_request`) ➔ 관리자가 일일이 승인"**하는 구조였습니다.
* **현실의 치명적 한계**:
  1. **개학 첫날 행정 마비**: 입사 당일 수백 명의 학생이 일제히 가입을 누르면, 사감실 직원은 종이 명단과 대조하며 수백 번 승인 버튼을 눌러야 합니다. 승인 지연으로 입실 직후 냉장고를 쓰지 못해 민원이 폭증합니다.
  2. **학기 전환 시 데이터 누수 (보안 리스크)**: 다음 학기 동일한 방(`205-1`)에 다른 학생이 입주했을 때, 이전 거주자의 물품 보관 이력, 벌점 기록, 사생활 메모가 새 학생에게 노출되거나 꼬일 위험이 구조적으로 존재했습니다.

### 2. 의사결정 (Decision)
* 공개 회원가입을 전면 폐기하고, 물리적 방/침대와 1:1 대응하는 **호실 슬롯(`resident_account_slot`) 사전 발급 생애주기제**를 도입했습니다.
* **입사 배정 (`check-in`)**: 관리자가 명단을 매핑하면 계정이 즉시 활성화되고 초기 비밀번호(`0000`)가 발급됩니다.
* **`0000` 보호 장치**: 최초 로그인 시 `must_change_password=true` 세션이 발급되며, **비밀번호 변경 전까지 시설 이용 및 개인정보 조회가 전면 차단(HTTP 403 `PASSWORD_CHANGE_REQUIRED`)**됩니다.
* **퇴사 및 데이터 완전 격리 (`check-out`)**: 퇴사 시 세션은 즉시 폐기되며, 차기 학기에 동일 호실 아이디(`205-1`)를 쓰더라도 **내부적으로 완전히 새로운 User UUID를 발급**하여 이전 학생의 데이터를 100% 영구 격리합니다.

### 3. 결과 및 가치 (Consequences)
* **관리자 행정 소요 0초**: 열쇠 배부 시 `"아이디: 205-1 / 초기비번: 0000"` 안내문 한 줄로 즉시 사용 가능.
* **완벽한 개인정보 보호**: 퇴사자-신규 입주자 간 데이터 오염 및 노출 리스크 원천 차단.

## ADR-002: 세탁실 마찰 감소와 신상 노출 트레이드오프

### 1. 배경 및 문제 (Context)
* 초기 설계에는 타인이 작동 중인 세탁기 시간을 ±10분 수정하는 '오차 정정'과 인앱 쪽지함 기능이 있었습니다. 이는 장난으로 남의 세탁 시간을 변경하는 트롤링을 유발할 소지가 컸습니다.
* 또한, 세탁이 끝난 빨래를 바구니로 옮겨 담은 후 전송하는 '수거 알림'에서 **발신자 신상을 어떻게 노출할 것인가**에 대한 심각한 고민이 있었습니다:
  * **완전 익명**: "내 빨래 누가 만졌어?"라는 도난 불안감 유발 및 장난성 허위 알림(트롤링) 리스크.
  * **완전 실명 (이름 + 연락처)**: 학생 간 사적인 대면 갈등 및 불필요한 프라이버시 침해.

### 2. 의사결정 (Decision)
* **시간 오차 정정 기능 제거 (ver3 백로그 이동)**: 시스템이 현장을 증명할 수 없고 트롤링 위험만 크므로 과감히 제외.
* **30자 수거 메모 + 발신자 호실('205호') 표기**:
  * 다음 사용자가 최대 30자 메모(예: `"3층 핑크색 바구니에 담아뒀어요"`, 미입력 시 디폴트 문구)를 작성하여 알림 전송.
  * 발신자 정보는 개인정보(이름/개인번호)를 숨기고 **호실 번호(예: `205호`)까지만 표기**.
* **기종별 최근 사용 시간 기억 (백엔드 로그 기반 구현)**:
  * 1번 세탁기에서 45분을 썼다면 다음날 4번 세탁기를 켜도 45분이 자동 완성되는 기능.
  * 프론트엔드 `localStorage`는 스마트폰↔노트북 기기 변경 시 동기화되지 않으므로, **백엔드의 `laundry_usage_log` 최근 1건 조회(`SELECT ... LIMIT 1`)로 구현하여 기기 무관 100% 영구 보장**.
* **종료 5분 전 자동 알림**: 개별 스마트폰 타이머를 맞출 필요 없이 시스템이 수거 준비 알림 자동 발송.

### 3. 결과 및 가치 (Consequences)
* **도난 오해 해소 & 책임감 부여**: "205호 학생이 옮겼다"는 최소한의 단서로 사감실 도난 신고 민원 예방.
* **프라이버시와 평화 유지**: 개인 연락처가 노출되지 않아 대면 마찰 없는 안전한 공동체 인터랙션 구축.

## ADR-003: 스터디룸 자원 독점 방지의 도메인적 해법

### 1. 배경 및 문제 (Context)
* 스터디룸(다목적실 3개)은 특정 학생의 장시간 독점이 가장 큰 이슈입니다.
* 이를 막기 위해 "주당 최대 시간 쿼터 알고리즘", "노쇼 신고 접수 ➔ 관리자 확인 ➔ 벌점 부과" 시스템을 도입하려 했습니다.
* **현실의 한계**:
  * 시험 기간 등 특수 상황마다 예외 규칙을 코드로 유지보수하기 어려움.
  * 관리자가 실제 방에 사람이 없었는지 현장 증명(CCTV 확인 등)이 불가능하여 허위 신고 및 판정 불복 민원 폭증.

### 2. 의사결정 (Decision)
* 복잡한 강제 제재 알고리즘 대신, **"투명한 달력 UI를 통한 사회적 제어(Social Pressure)"** 방식을 채택했습니다.
* **10분 단위 타임라인 & 실제 이용 인원 수(`attendeeCount`) 필수 입력**: 정밀한 시간 활용 지원.
* **과거/현재 예약자 투명 공개**: 달력 화면에서 과거와 현재 누가(호실 정보: 예 `205호`) 몇 시간 동안 방을 쓰고 있는지 전체 입주자에게 투명하게 노출.
* '합석' 용어는 공동체 친화적인 **'같이 이용'**으로 재정의하고 실시간 인원 변경 및 노쇼 판정 큐는 ver2 백로그로 격리.

### 3. 결과 및 가치 (Consequences)
* **추가 개발 비용 0원**: 복잡한 제재 알고리즘 없이 단순한 달력 조회 뷰 하나로 해결.
* **공동체 평판 효과**: 좁은 기숙사 공동체 특성상 남들에게 자신의 과도한 독점이 드러나므로 스스로 예약 시간을 자제하는 강력한 자율 억제력 발휘.

## ADR-004: YAGNI 원칙에 입각한 현장 중심 기능 다이어트

### 1. 배경 및 문제 (Context)
* 초기 시스템에는 대규모 이커머스나 협업 툴 수준의 엔터프라이즈 패턴들이 과도하게 설계되어 있었습니다:
  1. **다중 검사자 실시간 SSE 동기화 (`IN-306`)**: 2명의 층별장이 동시에 같은 칸을 열고 실시간 조치를 공유.
  2. **냉장고 칸 증설 시 호실 자동 재배분 시뮬레이션 알고리즘 (`reallocations/preview|apply`)**.
  3. **엔터프라이즈급 알림 쿼터제(일 2건) 및 발송 실패 추적 테이블**.

### 2. 의사결정 (Decision)
* **YAGNI (You Aren't Gonna Need It)** 원칙에 따라 탁상공론식 복잡도를 과감히 제거했습니다.
* **냉장고 검사**: 층별장 1명이 40~50분 동안 단독으로 수행하는 현장 현실을 반영하여 **1인 단독 세션 고정** (타 검사자 시도 시 409 반환).
* **냉장고 관리**: 기숙사 냉장고 교체/증설은 단순 물리적 추가(`INSERT`) 및 퇴역(`status = 'RETIRED'`) 모델로 충분하므로 수학적 재배치 시뮬레이션 알고리즘 폐기.
* **알림 센터**: 하루 수백 건 수준의 소규모 트래픽에 맞게 단순 인앱 알림 레코드와 cron 스케줄러 상수로 단순화.

### 3. 결과 및 가치 (Consequences)
* 백엔드/프론트엔드 코드 복잡도 **60% 이상 절감**.
* 네트워크 단절 및 분산 동기화 실패 포인트 원천 제거.

## ADR-005: AI 협업 시 오버엔지니어링 방지를 위한 물리적 문서 격리

### 1. 배경 및 문제 (Context)
* AI 어시스턴트(LLM)와 페어 프로그래밍을 진행할 때, 기획서에 "향후 ver2/ver3 확장 계획"이 조금이라도 적혀 있으면 AI는 불필요한 상위 추상 클래스, 빈 DTO 필드, 미사용 DB 컬럼을 선제적으로 만들어내는 오버엔지니어링(Context Drift)을 자주 일으킵니다.

### 2. 의사결정 (Decision)
* 프롬프트 제약에만 의존하지 않고, **문서 구조를 물리적으로 3개 영역으로 완전 격리**했습니다:
  1. `docs/specs/`: 현재 배포 대상인 **ver1 순수 명세만 보관** (다른 AI에게 제공하는 유일한 경로).
  2. `docs/backlog/`: 차기 확장 아이디어(ver2, ver3)를 격리 보관.
  3. `docs/archive/`: 구버전 회원가입제 등이 적힌 과거 기획 문서를 격리 보관.

### 3. 결과 및 가치 (Consequences)
* 다른 AI나 협업자에게 작업 위임 시 컨텍스트 오염 및 오버엔지니어링 발생률 **0% 달성**.

## ADR-006: 외부 분산 락(Redis) 배제와 PostgreSQL GiST 배타 제약을 통한 무결성 확보

### 1. 배경 및 문제 (Context)
* 스터디룸 예약 및 시설 슬롯 배정 시, 동일한 자원에 대해 동일 시간대에 2명 이상의 학생이 동시에 예약을 시도하는 동시성 충돌(Race Condition)이 발생할 수 있습니다.
* 흔히 이 문제를 해결하기 위해 Redis(Redisson) 분산 락을 도입하려 합니다.
* **현실의 한계**:
  * 추가 인프라(Redis) 운영 비용과 클라우드 배포 복잡도 증가.
  * 락 획득 타임아웃, 임대 시간(lease time) 만료 후 긴 트랜잭션 처리 중 동시 쓰기 발생, 네트워크 파티션 시 락 누수 등 분산 환경의 엣지 케이스 관리 부담.

### 2. 의사결정 (Decision)
* 외부 분산 캐시/락 인프라를 추가하지 않고, **PostgreSQL 자체 확장(`btree_gist`)의 범위 배타 제약(`EXCLUDE USING gist`)을 채택**했습니다.
* 스터디룸 예약 테이블(`study_room_reservation`)에 다음 제약 조건을 선언:
  ```sql
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  ALTER TABLE study_room_reservation
    ADD CONSTRAINT uq_study_room_no_overlapping_reservations
    EXCLUDE USING gist (
      room_id WITH =,
      tstzrange(start_at, end_at, '[)') WITH &&
    ) WHERE (status <> 'CANCELLED');
  ```
* 겹치는 시간대 예약이 인입될 경우, DB 엔진 레벨에서 즉시 배타 충돌 예외를 발생시키고, 스프링 백엔드는 이를 감지하여 사용자에게 HTTP 409 `RESERVATION_CONFLICT`를 반환합니다.

### 3. 결과 및 가치 (Consequences)
* **인프라 비용 0원 & 아키텍처 단순화**: 단일 RDBMS(PostgreSQL)의 ACID 특성을 100% 활용.
* **100% 원자적 동시성 무결성**: 트랜잭션 격리수준이나 앱 서버 다중화(스케일 아웃) 여부와 무관하게 데이터베이스 엔진이 물리적으로 중복 예약을 원천 차단.

## ADR-007: RFC 7807 규격화와 사용자 열거 공격(User Enumeration) 방어

### 1. 배경 및 문제 (Context)
* 웹 애플리케이션의 에러 응답 규격이 제각각이면 프론트엔드 연동 복잡도가 기하급수적으로 증가합니다.
* 특히 로그인/인증 실패 시 흔히 발생하는 보안 취약점:
  * "존재하지 않는 사용자입니다"와 "비밀번호가 일치하지 않습니다"를 구분하여 반환할 경우, 공격자가 임의의 학번/호실 목록을 무차별 대입(Brute-force)하여 **기숙사에 실제 등록된 학생의 아이디를 스캐닝(User Enumeration)**할 수 있습니다.
* 또한 에러 코드가 소문자(`validation_error`)와 대문자(`CAPACITY_EXCEEDED`)가 혼재되면 클라이언트 파싱 규칙이 깨집니다.

### 2. 의사결정 (Decision)
* **RFC 7807 호환 표준화**: `ProblemResponse` 레코드를 통해 `type`, `title`, `status`, `detail`, `instance`, `code` 표준 포맷 일원화.
* **대문자 스네이크 케이스(`SCREAMING_SNAKE_CASE`) 통일**: 모든 비즈니스 및 공통 에러 코드를 일관되게 규격화 (`VALIDATION_FAILED`, `SERVER_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `INVALID_CREDENTIALS` 등).
* **사용자 열거 공격 원천 차단**:
  * 아이디가 DB에 없는 경우와 비밀번호가 틀린 경우 모두 **동일한 HTTP 401 Unauthorized와 동일한 에러 코드 `"INVALID_CREDENTIALS"` 반환**.
  * **비활성(퇴사/미입사) 계정 상태 노출 방지**: 로그인 처리 시 계정 활성 상태(`user.status == ACTIVE`) 검사보다 **비밀번호 일치 검사(`passwordEncoder.matches`)를 먼저 수행**. 비밀번호를 모르는 외부 공격자에게는 퇴사/비활성 여부(`403 USER_INACTIVE`)조차 노출되지 않고 동일하게 `401 INVALID_CREDENTIALS`로 차단하여 내부 계정 상태 스캐닝을 원천 방어.

### 3. 결과 및 가치 (Consequences)
* **완벽한 계정 보안 무결성**: 외부 공격자가 기숙사 호실/아이디 등록 여부 및 퇴사 상태를 역추론할 수 없음.
* **프론트엔드-백엔드 간 명확한 인터페이스 계약**: 모든 HTTP 실패가 일관된 JSON 스키마로 반환되어 UI 에러 토스트 처리가 단순해짐.

## ADR-008: 도메인 식별자(UUID)와 사용자 인지용 라벨(INT)의 엄격한 분리

### 1. 배경 및 문제 (Context)
* 냉장고 보따리(Bundle)나 보관함 슬롯을 다룰 때, 화면에는 `"001"`, `"002"`, `"010"`과 같이 선행 0(Zero-padding)이 붙은 3자리 번호가 표시됩니다.
* 이를 DB에 문자열(`VARCHAR`)로 저장하면 다음과 같은 구조적 왜곡이 발생합니다:
  * 문자열 정렬 시 `"010"`이 `"002"`보다 먼저 오거나 뒤섞임 (`"1"`, `"10"`, `"2"` 정렬 오류).
  * 시퀀스 증가 및 번호 중복 검증 시 문자열 파싱 로직 필요.

### 2. 의사결정 (Decision)
* **내부 엔티티 식별자(Primary Key)**: 글로벌 고유성과 보안을 위해 UUID 사용.
* **사용자 표시용 라벨 번호**: DB 컬럼에는 순수 정수(`label_number INT`)로 저장.
* **3자리 패딩 포맷팅(`001`)**: DB나 비즈니스 로직에 관여시키지 않고, **프론트엔드 렌더링 계층 또는 응답 DTO 변환 시점(`String.format("%03d", labelNumber)`)에서만 포맷팅**.

### 3. 결과 및 가치 (Consequences)
* **데이터베이스 무결성 & 네이티브 정렬**: 숫자 인덱스를 통한 자연스러운 오름차순 정렬(`ORDER BY label_number ASC`) 및 범위 검색 보장.
* **관심사의 분리**: 표시 형식 변경(예: 3자리 -> 4자리)이 발생해도 데이터베이스 스키마와 쿼리가 영향을 받지 않음.

## ADR-009: 시간대 단일 기준선(UTC Baseline)과 표시 시점 분리

### 1. 배경 및 문제 (Context)
* 서버 호스트와 데이터베이스 컨테이너의 시간대 설정(KST, UTC, 로컬 머신)이 서로 다르면, 예약 시간 비교, 만료 시간 처리, 세탁 로그 조회 등에서 9시간 시차 버그가 발생합니다.

### 2. 의사결정 (Decision)
* **저장 및 연산 기준선**: 데이터베이스(`TIMESTAMPTZ`), 백엔드 도메인 엔티티(`OffsetDateTime` 또는 `Instant`) 모두 **UTC 단일 기준선으로 영속화 및 계산**.
* **클라이언트 표시 시점 변환**: KST(`Asia/Seoul`) 표시는 API 직렬화 계층 또는 프론트엔드 브라우저 로케일에 맞춰 변환.

### 3. 결과 및 가치 (Consequences)
* 배포 환경(로컬 Docker, AWS ECS, GCP Cloud Run 등)의 호스트 타임존 설정에 영향을 받지 않는 영구적 시간 무결성 확보.

## ADR-010: 공용 엔드포인트에서의 역할별 암묵적 권한 스코프(Implicit Scope)와 파라미터 무력화

### 1. 배경 및 문제 (Context)
* 냉장고 슬롯 조회(`GET /fridge/slots`)는 일반 거주자뿐만 아니라 층별장(Floor Manager)과 관리자(Admin)도 함께 사용하는 공용 엔드포인트입니다.
* 관리자나 층별장은 층별 필터(`floor`)나 검사용 상세 뷰(`view=full`)가 필요하지만, 이를 일반 거주자에게도 동일하게 허용하면 다음과 같은 문제가 생깁니다:
  1. **접근 제어 착시 및 파라미터 변조(Tampering) 시도**: 일반 거주자가 `floor=3` 등을 전송하여 다른 층의 슬롯을 보려고 시도할 수 있습니다.
  2. **과도한 확장성**: 거주자 화면에서 쓰이지도 않는 불필요한 뷰 모드가 열려 있으면 데이터 노출 범위가 넓어집니다.

### 2. 의사결정 (Decision)
* **엔드포인트 분리 대신 역할별 서버 강제 스코프(Role-based Implicit Scope) 채택**:
  * 엔드포인트를 `/resident/slots`, `/manager/slots` 등으로 과도하게 쪼개지 않고 단일 `GET /fridge/slots`를 유지하되, **서버 내부에서 호출 주체의 역할에 따라 파라미터 처리 정책을 엄격히 차등화**했습니다:
    1. **일반 거주자 (`RESIDENT`)**: 클라이언트가 `floor` 파라미터를 넘기더라도 이를 완전히 무시(무력화)하고, 오직 **서버 세션에 바인딩된 배정 호실의 칸(`accessibleCompartmentIds`)만 강제 반환**.
    2. **층별장 (`FLOOR_MANAGER`)**: 자신이 담당하는 층 외의 `floor`를 요청하면 즉시 **HTTP 403 `FLOOR_SCOPE_VIOLATION`**으로 거부.
    3. **검사 워크플로우**: `view=full` 파라미터는 실제 점검/검사 화면([inspections/api.ts](file:///Users/hyun/Documents/GitHub/DormMate/frontend/features/inspections/api.ts))에서 전체 슬롯의 잠금 상태를 파악해야 하는 구체적인 목적에 한해서만 선택적으로 활성화.

### 3. 결과 및 가치 (Consequences)
* 거주자의 파라미터 변조를 통한 타 층/타 호실 자원 엿보기 원천 차단.
* 엔드포인트 난립 없이 단일 API 안에서 보안 무결성과 검사 워크플로우를 완벽히 양립.

## ADR-011: 시간 경계 연속성([startedAt, endedAt))과 결정적 페이징 정렬

### 1. 배경 및 문제 (Context)
* 방 이동, 슬롯 재할당 등 거주 이력을 관리할 때, 이전 할당의 종료 시각과 신규 할당의 시작 시각을 각각 `now()`로 호출하면 나노초 단위의 시각 차이로 인해 **권한 공백(순간적 미거주)**이나 **권한 중복(순간적 2개 방 배정)**이 발생할 수 있습니다.
* 또한 DB 페이징 조회 시 정렬 조건에 고유 식별자(PK)가 포함되지 않으면, RDBMS 엔진의 실행 계획에 따라 페이지를 넘길 때 동일한 데이터가 중복 노출되거나 누락되는 비결정적 페이징(Non-deterministic Pagination) 문제가 발생합니다.

### 2. 의사결정 (Decision)
* **반개구간 시간 경계(`[startedAt, endedAt)`)**:
  * 시작 시각 포함, 종료 시각 제외 표준을 채택.
  * 방 이동/퇴사 시 단일 `Instant` 타임스탬프를 1회만 발급하여 이전 레코드의 `releasedAt`과 신규 레코드의 `assignedAt`에 동일하게 부여함으로써 권한 공백을 0초로 차단.
* **결정적 정렬(Deterministic Pagination)**:
  * 모든 페이징 목록 조회 쿼리의 마지막 정렬 조건으로 항상 고유 식별자(`ORDER BY ... ASC, id ASC`)를 고정하여 페이지 이동 시 순서 일관성을 100% 보장.

### 3. 결과 및 가치 (Consequences)
* 이력 데이터의 나노초 단위 무결성 및 페이징 안정성 완벽 확보.

## ADR-012: 파생 데이터의 DB 저장 배제와 이력 기반 DTO 합성 원칙

### 1. 배경 및 문제 (Context)
* 관리자 사용자 목록 화면 등에서 `room_code`("205호"), `floor_code`("2층"), `total_penalties`(총 벌점)와 같은 조합/집계 정보가 필요합니다.
* 이를 빠르게 조회하기 위해 `dorm_user` 테이블에 컬럼으로 중복 저장(Denormalization)하려는 유혹이 있습니다.
* **현실의 문제점**:
  * 학생이 방을 이동하거나 벌점이 정정/취소될 때, 파생 컬럼을 함께 갱신하지 않으면 원천 데이터(`room`, `penalty_history`)와 파생 컬럼 간 정합성이 깨집니다.

### 2. 의사결정 (Decision)
* **원천 단일 진실 공급원(SSOT, Single Source of Truth) 유지**:
  * DB에는 원천 이벤트(`room.floor`, `room.room_number`, `penalty_history` 이력 행)만 영속화합니다.
* **표현 계층 DTO 합성**:
  * `"205호"` 등의 표시값은 DTO 매퍼에서 합성(`room.floor + room.roomNumber`)하고, 총 벌점은 집계 쿼리(`SUM/COUNT`) 또는 비즈니스 서비스 계층에서 계산하여 응답합니다.

### 3. 결과 및 가치 (Consequences)
* 데이터베이스 동기화 누락으로 인한 정합성 오류 원천 차단.
* 표시 형식 변경 시 DB 마이그레이션 없이 애플리케이션 DTO 매퍼 수정만으로 유연하게 대처.

## ADR-013: H2 배제와 Testcontainers(PostgreSQL 16) 결정론적 테스트 기준선

### 1. 배경 및 문제 (Context)
* 스프링 부트 프로젝트에서 흔히 빠른 속도를 이유로 H2 인메모리 DB를 테스트 환경으로 사용합니다.
* **현실의 치명적 한계**:
  * PostgreSQL의 고유 기능인 GiST 범위 배타 제약(`EXCLUDE USING gist`), `tstzrange`, `TIMESTAMPTZ` 타임존 처리 등을 H2는 온전히 지원하지 못합니다.
  * H2에서는 테스트가 통과하지만 실제 운영 PostgreSQL에서는 DDL 에러나 동시성 제약 예외가 터지는 **"가짜 성공(False Positive)"**이 발생합니다.
  * 또한 로컬 머신에 설치된 PostgreSQL에 의존하면 개발자마다 DB 포트, 계정, 버전 차이로 인해 테스트 재현성이 깨집니다.

### 2. 의사결정 (Decision)
* **Testcontainers (PostgreSQL 16) 표준화**:
  * `AbstractPostgresIntegrationTest` 베이스 클래스를 통해 실제 운영 환경과 100% 동일한 PostgreSQL 16 공식 도커 컨테이너를 동적으로 구동하여 테스트 실행.
* **테스트 슬라이스 분리**:
  * DB가 필요 없는 순수 WebMvc 유효성 검증 테스트는 가벼운 MockMvc 슬라이스로 분리하여 전체 테스트 속도 최적화.

### 3. 결과 및 가치 (Consequences)
* 로컬 DB 설치 상태와 무관한 **결정론적(Deterministic)이고 100% 재현 가능한 테스트 기준선** 확보.
* PostgreSQL 전용 고급 기능(GiST 배타 락, 타임존 등)의 동작 무결성을 빌드 타임에 완벽히 보장.

## ADR-014: 불완전한 임시 상태(Empty Bundle) 배제와 Fail-Fast 원자적 생성 원칙

### 1. 배경 및 문제 (Context)
* 냉장고 물품 보따리(Bundle) 등록 시, "임시 저장을 위해 아이템이 0개인 빈 보따리도 저장을 허용하자"는 기획 아이디어가 검토된 적이 있습니다.
* **현실의 문제점**:
  * 아이템이 0개인 빈 보따리가 DB에 저장된 채 사용자가 이탈하면, 냉장고 칸의 용량(`capacity`) 계산을 왜곡하고 쓰레기 데이터(Ghost Data)가 누적됩니다.
  * 추후 유령 보따리를 정리하기 위한 복잡한 만료/정리 배치 작업이 강제됩니다.

### 2. 의사결정 (Decision)
* **Fail-Fast 유효성 검증 & 원자적 생성**:
  * API 요청 DTO([CreateBundleRequest](file:///Users/hyun/Documents/GitHub/DormMate/backend/src/main/java/com/dormmate/backend/modules/fridge/presentation/dto/CreateBundleRequest.java)) 레벨에서 `@NotEmpty List<CreateBundleItemInput> items` 제약을 강제.
  * 최소 1개 이상의 유효한 물품이 포함된 완전한 상태일 때만 보따리 생성을 허용(0개 요청 시 HTTP 422 `VALIDATION_FAILED` 즉시 거부).

### 3. 결과 및 가치 (Consequences)
* 유령 데이터 축적 및 냉장고 용량 계산 왜곡 원천 방지.
* 별도의 만료 데이터 정리 배치 스케줄러가 필요 없는 단순하고 무결한 데이터 생명주기 달성.

## ADR-015: 냉장고 물품 기입 시스템의 본질과 행동 기반 관리자 에스컬레이션(Actionable Admin Governance)

### 1. 배경 및 문제 (Context)
* 기숙사 운영 중 도서 연체, 세탁물 장기 방치, 스터디룸 직전 취소 등 공동생활 마찰이 발생할 때, 이를 즉각적인 자동 전역 시설 차단으로 강제하려는 엔지니어링 유혹이 있습니다.
* **현실의 본질적 한계**:
  1. **냉장고 시스템의 본질**: 냉장고는 물리적 스마트 도어락이 아니라, **거주자가 보관할 물품을 스스로 기입하고 유통기한을 관리하는 위생 보조 소프트웨어**입니다. 벌점이 높다고 물품 등록 기능을 차단하면 오히려 스티커 없는 무단 방치 음식물만 양산되어 위생이 파탄납니다.
  2. **미협의된 자동 제재의 역효과**: 사감실과 공식 규정으로 합의되지 않은 '벌점 10점 시 세탁실 차단'을 시스템이 독단적으로 집행하면 학생 민원만 폭증합니다.
  3. **방치 위험**: 그렇다고 로그만 쌓아두고 관리자에게 알리지 않으면 연체 도서가 영영 회수되지 않고 방치됩니다.

### 2. 의사결정 (Decision)
* **냉장고 물품 기입 권한 상시 보장**:
  * 위생 관리의 본질을 위해 **냉장고 물품 등록 및 라벨 조회 기능은 어떠한 제재에서도 영구 제외**합니다.
* **도메인 자연 제약 (Local Natural Rule)**:
  * **도서관 연체 도서 보유 시 추가 대출 차단**: 전 세계 도서관의 상식적인 규칙을 적용하여, 연체 도서를 반납하기 전까지는 신규 대출을 즉시 차단합니다.
* **3단계 행동 기반 관리자 에스컬레이션 (Actionable Escalation)**:
  1. *1단계 (학생 자동 독촉)*: 연체 1~3일째 학생에게 아침 9시 리마인더 전송.
  2. *2단계 (관리자 대시보드 Action Required 시각화)*: 연체 7일 이상 경과 시, 관리자 웹 화면(`/admin`) 최상단에 **[조치 필요] 배지 카드(호실, 학생명, 도서명)**를 띄워 사감실 직원이 즉시 파악.
  3. *3단계 (Daily Admin Digest)*: 매일 09:00 배치 시 장기 연체/방치 건수 요약 리포트를 관리자에게 딱 1회 전달하여 오프라인 행정/면담으로 연계.

### 3. 결과 및 가치 (Consequences)
* 물품 등록 차단으로 인한 미등록 부패 음식물 양산 방지 (위생 무결성 유지).
* 관리자에게 무차별 푸시 알림을 쏘는 '알림 공해' 없이, **대시보드 로그인 시 1초 만에 조치 대상이 파악되는 현장 친화적 운영 가시성 확보**.

## ADR-016: 수기 표기의 한계 극복과 보따리(Bundle) 모델을 통한 규정 진화(Rule Evolution) 수용성 확보

### 1. 배경 및 문제 (Context)
* 현실 기숙사의 최신 공유냉장고 관리 규정에는 "밀폐용기 2개 이내, 지퍼백 2개 이내, 외부 스티커에 가장 짧은 유통기한 1개만 표기"라는 엄격한 물리적 하드 리밋(Hard Limit)이 존재합니다.
* **근본 원인 분석 (Root Cause)**:
  * 이러한 경직된 규정은 본질적인 냉장고 보관의 한계라기보다는 **"종이 스티커에 펜으로 적는 수기 표기(Analog Handwriting)의 정보 전달 한계"** 때문에 만들어진 임시방편적 규제입니다.
  * 종이 스티커 한 장에는 용기 안에 어떤 음식이 몇 개 들어있는지 다 적을 수 없으므로, 내용물을 알 수 없는 관리 주체 입장에서는 "용기 2개까지만 넣어라"는 식의 거친 물리적 규제를 둘 수밖에 없었습니다.
* **엔지니어링 딜레마**:
  * 만약 이 아날로그 규제를 앱 데이터베이스 스키마나 API 유효성 검증(`ck_max_locknlock_2` 등)에 하드코딩해버리면,
  * 향후 DormMate가 도입되어 내용물의 투명성이 확보되고 행정 규정이 "슬롯/용량 기반 자율 관리"로 개정되었을 때 **소프트웨어 데이터 모델을 전면 수정해야 하는 아키텍처적 취약성(Fragility)**이 발생합니다.

### 2. 의사결정 (Decision)
* **보따리(Bundle) 추상화 유지**:
  * 물리적 용기(지퍼백, 락앤락)의 개수나 규격을 테이블 컬럼으로 쪼개지 않고, 하나의 물리적 용기를 자연스럽게 추상화한 **'보따리(Bundle) - 아이템(Item)' 구조를 단일 진실 공급원(SSOT)으로 유지**.
* **규정 진화(Rule Evolution) 수용성 확보**:
  * 앱에서 보따리 안의 아이템들과 각각의 유통기한을 100% 투명하게 관리함으로써 수기 표기의 한계를 소프트웨어로 극복.
  * 현행 기숙사 룰(밀폐용기 2개, 지퍼백 2개 등)은 프론트엔드 안내 가이드 및 정책 유효성 검증 계층(Policy Validation Layer)에서 유연하게 제어하여, **데이터 모델 변경 없이도 미래의 행정 규정 완화/진화를 100% 수용**.

### 3. 결과 및 가치 (Consequences)
* **도메인 회복탄력성(Anti-Fragile Architecture)**: 아날로그 행정 규칙의 변화에 흔들리지 않는 견고한 데이터 모델 확보.
* **소프트웨어를 통한 현장 혁신**: 단순 전산화를 넘어, 소프트웨어의 투명성을 통해 현실의 불합리한 행정 규칙 자체를 더 단순하고 효율적인 방향으로 개선할 수 있는 기술적 토대 마련.

## 🎯 [부록] 면접관 예상 질문 & 모범 답변 스크립트

### Q1. "일반적인 회원가입 승인제를 쓰지 않고, 왜 사전 발급 슬롯 방식을 썼나요?"
> **답변 핵심**: "기숙사는 오픈마켓 같은 B2C 서비스가 아니라, 학기 시작 전에 이미 물리적인 방과 거주자가 확정되어 있는 폐쇄형 B2B 도메인입니다. 학생이 가입하고 관리자가 승인하는 방식은 개학 첫날 수백 건의 승인 대기 병목과 민원을 유발합니다. 또한 다음 학기 동일한 방에 새 학생이 입주했을 때 이전 거주자의 데이터가 노출될 위험이 컸습니다. 따라서 물리적 침대와 1:1 매핑되는 호실 슬롯을 사전 발급하고, 0000 강제 변경과 퇴사 시 신규 User UUID 발급을 도입하여 행정 소요를 0초로 줄이고 데이터 격리를 100% 달성했습니다."

### Q2. "세탁물 수거 알림에서 발신자 정보를 왜 '호실'까지만 노출했나요?"
> **답변 핵심**: "완전 익명성과 완전 실명성 사이의 트레이드오프를 도메인 심리 관점에서 풀었습니다. 완전 익명으로 두면 장난으로 알림을 보내는 트롤링이 발생하고 내 빨래를 누가 만졌는지 몰라 도난 불안감이 커집니다. 반면 실명과 연락처를 노출하면 학생 간 사적인 대면 마찰이 발생합니다. 따라서 '205호 학생이 옮겼다'는 최소한의 호실 정보만 노출하여 장난을 방지하고 책임감을 부여하면서도, 개인 프라이버시를 안전하게 지키는 최적의 절충안을 도출했습니다."

### Q3. "스터디룸 독점을 막기 위해 왜 복잡한 쿼터 알고리즘 대신 달력 UI를 택했나요?"
> **답변 핵심**: "소프트웨어로 모든 것을 강제하기보다 공동체의 '소셜 프레셔(Social Pressure)'를 활용하는 것이 훨씬 비용 효율적이라고 판단했습니다. 주당 최대 시간 제한이나 노쇼 벌점 시스템을 코드로 짜면 시험 기간 같은 예외 상황마다 코드를 고쳐야 하고, 현장 증명이 불가능해 사감실 민원만 폭증합니다. 대신 과거와 현재 누가 방을 몇 시간 동안 쓰고 있는지 투명하게 공개하는 달력 UI를 적용하여, 공동체 평판 효과를 통해 추가 개발 비용 0원으로 자발적 독점 억제를 유도했습니다."

### Q4. "기획했던 많은 기능들을 ver2/ver3로 미루고 설계를 대폭 축소한 이유는 무엇인가요?"
> **답변 핵심**: "철저히 YAGNI(You Aren't Gonna Need It) 원칙에 입각했습니다. 다중 검사자 실시간 SSE 동기화나 냉장고 재배분 시뮬레이션 알고리즘 등은 실제 1인 검사 현장이나 몇 년에 한 번 있을까 말까 한 물리적 이벤트에 비해 지나치게 과도한 엔터프라이즈 아키텍처였습니다. 앞으로 일어날지 모르는 희박한 가정을 위해 현재의 아키텍처를 복잡하게 만들기보다는, 핵심 사용자 루프(입사 ➔ 냉장고 ➔ 세탁기 ➔ 스터디룸)를 가장 가볍고 실패 없이 동작시키는 데 집중했습니다."

### Q5. "스터디룸 예약의 시간 겹침(동시성 충돌)을 Redis 분산 락 대신 데이터베이스 제약으로 해결한 이유는 무엇인가요?"
> **답변 핵심**: "스터디룸 3개라는 도메인 규모에서 Redis 분산 락을 도입하는 것은 불필요한 인프라 오버엔지니어링이라고 판단했습니다. 분산 락은 네트워크 단절, TTL 만료 후 긴 트랜잭션 등 관리해야 할 엣지 케이스가 많습니다. 반면 PostgreSQL의 `btree_gist` 확장을 이용한 `EXCLUDE USING gist` 제약은 단일 DB 엔진의 ACID 트랜잭션 안에서 겹치는 시간 범위를 100% 원자적으로 차단합니다. 인프라 비용과 관리 포인트를 늘리지 않고도 완벽한 무결성을 달성했습니다."

### Q6. "로그인 실패 시 왜 아이디 불일치와 비밀번호 불일치를 구분하지 않고 동일하게 처리했나요?"
> **답변 핵심**: "사용자 열거 공격(User Enumeration Attack)을 방어하기 위한 보안 표준을 준수했습니다. '존재하지 않는 아이디'라는 에러를 노출하면 악의적 사용자가 기숙사 호실 번호나 학번 목록을 대입해보며 실제 가입된 계정을 식별해낼 수 있습니다. 또한 퇴사/비활성 계정 검사보다 비밀번호 일치 검사를 먼저 수행하여, 비밀번호를 모르는 공격자에게는 퇴사 상태조차 노출되지 않고 동일하게 `401 INVALID_CREDENTIALS`를 반환하도록 설계했습니다."

### Q7. "화면에 '001', '002'로 표시되는 라벨을 DB에 문자열이 아닌 INT로 저장한 이유는 무엇인가요?"
> **답변 핵심**: "영속 계층의 데이터 무결성과 표현 계층(UI)의 포맷팅 관심사를 엄격히 분리하기 위함입니다. 선행 0을 포함한 문자열로 저장하면 DB에서 '010'이 '002'보다 앞에 정렬되는 사전식 정렬 왜곡이 발생하고, 시퀀스 유효성 검증도 번거로워집니다. 따라서 데이터베이스에는 순수 정수(`INT`)로 저장하여 자연스러운 숫자 정렬과 인덱싱 무결성을 확보하고, 3자리 패딩(`001`)은 프론트엔드 또는 DTO 변환 시점에서 처리하도록 설계했습니다."

### Q8. "전역 에러 응답 규격을 RFC 7807 표준으로 정의한 이유는 무엇인가요?"
> **답변 핵심**: "API 소비자인 프론트엔드와의 계약(Contract)을 명확히 하고 예외 처리 일관성을 확보하기 위해서입니다. RFC 7807 호환 `ProblemResponse` 포맷을 적용하고 모든 에러 코드를 SCREAMING_SNAKE_CASE(`VALIDATION_FAILED`, `SERVER_ERROR` 등)로 표준화함으로써, 프론트엔드 개발자가 특정 엔드포인트마다 다른 예외 객체를 파싱할 필요 없이 일관된 토스트 메시지 및 필드 유효성 검증 UI를 렌더링할 수 있게 구축했습니다."

### Q9. "냉장고 슬롯 조회 API에서 거주자의 층(floor) 접근을 어떻게 제어했나요?"
> **답변 핵심**: "최소 권한의 원칙과 역할별 암묵적 스코프(Implicit Scope)를 적용했습니다. 엔드포인트를 거주자용과 관리자용으로 파편화하지 않고 단일 `GET /fridge/slots`로 유지하되, 거주자가 인입되면 클라이언트가 넘긴 `floor` 파라미터 유무와 무관하게 서버 토큰에 바인딩된 배정 호실의 칸(`accessibleCompartmentIds`)으로만 강제 필터링하여 타 층 자원 엿보기를 원천 차단했습니다. 반면 층별장은 비인가 층 요청 시 403 `FLOOR_SCOPE_VIOLATION`을 반환하도록 하여, 단일 API 안에서 보안과 운영 편의성을 모두 달성했습니다."

### Q10. "방 이동이나 슬롯 재배정 시 시간 경계를 어떻게 관리했나요?"
> **답변 핵심**: "시작 포함, 종료 제외의 반개구간(`[startedAt, endedAt)`) 표준을 적용했습니다. 방 이동 시 단일 `Instant` 객체를 한 번만 발급하여 이전 방의 `releasedAt`과 새 방의 `assignedAt`에 동일한 시점을 원자적 트랜잭션으로 부여했습니다. 이를 통해 `now()`를 두 번 호출할 때 발생하는 나노초 단위의 권한 공백(순간적 미거주)이나 권한 중복을 원천 차단했습니다."

### Q11. "단위/통합 테스트 시 왜 H2 인메모리 DB 대신 Testcontainers(PostgreSQL)를 사용했나요?"
> **답변 핵심**: "실제 운영 환경과의 환경 격차(Parity)로 인한 가짜 성공(False Positive)을 방지하기 위함입니다. 저희 시스템은 PostgreSQL 전용 고급 기능인 GiST 배타 제약(`tstzrange`), `TIMESTAMPTZ` 등을 적극 활용하는데, H2는 이를 완벽히 지원하지 못합니다. 따라서 로컬 개발 장비 환경에 영향받지 않으면서도 실제 운영 환경과 100% 동일한 PostgreSQL 16 공식 도커 컨테이너를 Testcontainers로 동적 구동하여, 배포 전 데이터베이스 제약과 쿼리 무결성을 빌드 타임에 완벽히 검증했습니다."

### Q12. "총 벌점이나 호실 표시명 같은 파생 데이터를 DB 컬럼으로 저장하지 않은 이유는 무엇인가요?"
> **답변 핵심**: "단일 진실 공급원(SSOT) 원칙을 지켜 데이터 불일치를 원천 차단하기 위함입니다. '205호' 같은 호실 명칭이나 총 벌점을 편의상 컬럼에 중복 저장(비정규화)하면, 방 변경이나 벌점 차감/취소 시 컬럼 갱신이 누락되어 정합성이 깨지는 버그가 발생합니다. 따라서 DB에는 원천 이벤트(`room`, `penalty_history`)만 영속화하고, 사용자 노출 값은 DTO 매핑 시 합성하거나 서비스 집계로 계산하여 데이터 무결성을 100% 보장했습니다."

### Q13. "물품 보따리(Bundle) 등록 시 빈 보따리(0개 아이템) 임시 저장을 허용하지 않은 이유는 무엇인가요?"
> **답변 핵심**: "유령 데이터(Ghost Data) 양산과 냉장고 용량 계산 왜곡을 방지하기 위함입니다. 아이템이 0개인 빈 보따리 생성을 허용하면 사용자가 등록 도중 이탈했을 때 DB에 쓰레기 데이터가 누적되고, 냉장고 슬롯의 활성 보따리 수(`occupiedCount`)를 왜곡하게 됩니다. 이를 정리하기 위해 만료 배치 스케줄러를 추가하는 것은 불필요한 복잡도이므로, DTO 레벨에서 `@NotEmpty`로 최소 1개 이상의 아이템을 강제하여 완전한 상태의 엔티티만 원자적으로 저장되도록 Fail-Fast 원칙을 적용했습니다."

### Q14. "연체 도서 방치나 이용 마찰을 관리자에게 어떻게 효과적으로 전달했나요?"
> **답변 핵심**: "무차별 푸시 알림으로 관리자를 피로하게 만드는 대신, '3단계 행동 기반 에스컬레이션(Actionable Escalation)'을 설계했습니다. 1~3일 연체는 학생 본인에게만 아침 9시에 자동 독촉을 보내고, 7일 이상 장기 연체되면 관리자 웹 대시보드 최상단에 [조치 필요] 배지로 호실(205호)과 도서명을 즉시 시각화했습니다. 또한 매일 아침 9시 배치로 1일 1회 요약 리포트를 전달하여, 사감실 직원이 출근 후 로그인 한 번으로 오늘 처리할 이상 징후를 1초 만에 파악하고 오프라인 면담으로 연결할 수 있는 현장 친화적 거버넌스를 구축했습니다."

### Q15. "현실 기숙사 규정(락앤락 2개, 지퍼백 2개)을 시스템에 하드코딩하지 않고 보따리(Bundle) 모델을 유지한 이유는 무엇인가요?"
> **답변 핵심**: "현실의 경직된 용기 규정은 냉장고 자체의 한계가 아니라, 종이 스티커 수기 표기(Analog Handwriting)의 정보 전달 한계로 인해 만들어진 임시방편적 규제였기 때문입니다. 소프트웨어가 도입되어 보따리 내부 음식과 유통기한이 투명하게 관리되면 현실의 행정 규칙 자체가 더 유연하게 진화할 가능성이 높습니다. 따라서 임시적인 물리적 제한을 DB 스키마에 하드코딩하여 결합도를 높이기보다, 유연한 '보따리(Bundle) - 아이템(Item)' 구조로 추상화하여 소프트웨어의 투명성을 확보함과 동시에 향후 행정 규칙 진화에도 데이터 모델 변경 없이 100% 대응할 수 있도록 설계했습니다."
